## Failure Scenarios

### PM-01 — Mutable donor drift
- Failure: a donor changes after pack approval, but integration proceeds using new bytes.
- Signal: donor Git status or file inventory differs from the activation pins.
- Mitigation: complete pre-write donor inventories and immediate fail-closed equality check.

### PM-02 — 0.2.3 proof is overclaimed for 0.2.5
- Failure: prior deterministic evidence is presented as combined-candidate qualification.
- Signal: closeout cites MS-05 without new 0.2.5 postimages and regression evidence.
- Mitigation: treat prior evidence as provenance only; require a new bounded 0.2.5 verdict.

### PM-03 — Textual merge drops 0.2.5 safeguards
- Failure: applying the repair diff removes cache integrity, approval labels, direct Factory-command passthrough, or nested capability evidence.
- Signal: named 0.2.5 regression tests disappear or change semantics.
- Mitigation: behavior-level collision matrix, test union, and pre-builder authored gate.

### PM-04 — Public reason-code regression
- Failure: operators and docs expect `FACTORY_BMAD_NON_CANONICAL_LAYOUT`, but runtime emits only a new granular code.
- Signal: Doctor/Audit tests or quick-start assertions fail.
- Mitigation: stable public code plus subordinate granular cause; separate unsafe activation code.

### PM-05 — Factory commands are blocked
- Failure: repository BMAD markers cause `/factory:*` or `/factory-bmad:*` commands to enter malformed BMAD classification.
- Signal: direct command coexistence tests fail before expansion.
- Mitigation: explicit passthrough and both direct/model-initiated negative coverage.

### PM-06 — Generated packages become a second source
- Failure: donor-generated bytes are copied or hand-edited.
- Signal: builder parity or ownership manifests disagree with authored source.
- Mitigation: protect generated roots until authored PASS; exactly one canonical replacement.

### PM-07 — Solution context becomes implementation authority
- Failure: architecture/spec output marked “final” drives code or satisfies a Factory gate.
- Signal: promotion/preflight accepts binding or execution-ready claims.
- Mitigation: typed `EVIDENCE_ONLY`, claim dispositions, hostile authority fixtures, and permanent delivery denials.

### PM-08 — Unsafe layout fails open
- Failure: an allowed discovery or solution workflow runs while nested, partial, ambiguous, or symlinked BMAD is active.
- Signal: any allowed-workflow sentinel executes under unsafe activation.
- Mitigation: uniform pre-allowlist denial and layout-case matrix.

### PM-09 — Disposable proof is smuggled into integration
- Failure: BMAD workflows or AuditEdge are invoked to “finish verification.”
- Signal: evidence contains workflow execution or target access.
- Mitigation: integration status ceiling, protected external roots, and stop before MS-06.

### PM-10 — Existing checkout is damaged
- Failure: uplift, repair, video, pilot, or registration state changes during integration.
- Signal: complete before/after donor/Git inventories differ.
- Mitigation: read-only donors, no-touch lifecycle checks, halt on first mismatch.

### PM-11 — Test or builder creates residue
- Failure: bytecode, temp output, or repeated builder execution pollutes source or evidence.
- Signal: post-run inventory includes cache/residue or invocation count exceeds plan.
- Mitigation: Factory Python wrapper, bounded external evidence, explicit builder-call accounting.

### PM-12 — Documentation outruns evidence
- Failure: project state says MS-06/pilot/rollout ready after deterministic integration only.
- Signal: claims exceed `FACTORY_BMAD_025_INTEGRATION_DETERMINISTICALLY_QUALIFIED`.
- Mitigation: vocabulary scan and separate human checkpoints.

## Top Three
1. PM-03: overlapping runtime policy makes silent loss of 0.2.5 safeguards likely without semantic reconciliation.
2. PM-08: a fail-open unsafe layout would defeat the governance boundary even if most tests pass.
3. PM-10: dirty donor work is user-owned and must never become collateral damage.
